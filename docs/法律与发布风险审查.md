# 法律与发布风险审查

更新时间：`2026-07-05`

说明：这不是律师意见，而是基于当前仓库内容、应用行为和公开常识做的发布前工程审查。

## 结论摘要

当前项目在“保持 MIT、商店免费”的路线下可以继续推进，但还存在几类需要明确接受的残留风险。

## 主要风险

### 1. 第三方服务条款风险

风险级别：`高`

原因：

- 软件明确面向 `Battle.net / 魔兽世界` 本地账号切换
- 代码中存在读取、恢复和改写本地状态的逻辑
- 即使软件本身不自动化游戏行为，也仍可能被第三方平台视为不受支持的第三方工具

实际含义：

- 这类风险不能靠 `EULA` 或隐私政策完全消除
- 最稳妥的做法是避免在商店文案里夸大“官方兼容”或“安全无风险”
- 需要持续保留“不隶属、不保证符合第三方条款、用户自行判断”的说明

### 2. 品牌与关联暗示风险

风险级别：`中`

原因：

- 仓库和产品相关文档中会出现 `Battle.net`、`Blizzard`、`World of Warcraft` 等第三方名称，且技术层仍保留历史账号导入相关表述
- 如果商店描述或 UI 给人“官方合作、官方工具、官方支持”的印象，就会放大风险

当前处理建议：

- 保留必要的功能性提及
- 明确写出“独立第三方工具，不隶属于 Blizzard 或 Battle.net”
- 避免使用对方官方 Logo、品牌主视觉或容易误认的图形组合

### 3. 历史残留代码风险

风险级别：`中到高`

当前发现：

- 发布前曾存在根目录旧壳文件，包含第三方远程域名、旧实例隔离逻辑、下载器、协议处理和插件安装等历史痕迹

判断：

- 这些内容不属于当前发布主线
- 但只要继续留在仓库里，就会在代码审查、合规说明、版权归属自查中制造疑点

当前处理：

- 已将确认无用的旧壳文件从当前主线移除
- 后续仍应避免把历史打包产物、旧下载器或远程资源代码重新带回仓库

### 4. 历史来源与实现独立性风险

风险级别：`中`

原因：

- 当前产品虽然已经移除了历史导入功能，但仓库和设计资料里仍可能保留早期研究痕迹
- 如果将来证明某些旧逻辑、资产或结构直接复制自第三方受保护实现，风险仍会升高

当前从仓库表面能确认的情况：

- 当前主线源码没有保留面向旧工具的导入功能
- 我没有在当前主线源文件中看到直接联网调用第三方历史在线接口的行为

仍无法仅靠仓库静态检查排除的点：

- 某些历史逻辑、逆向结论或旧文件是否直接来源于对方产品
- 某些图标、文本、配置结构是否足以被主张构成复制

### 5. 软件内外链风险

风险级别：`中`

原状态问题：

- 应用页脚可承载多个外部 GitHub 推广链接
- 主进程原先对 `openExternal` 没有限制，理论上只要渲染层传入 URL 就可打开外部页面

已做的收紧：

- 现在只允许打开登记在白名单中的 GitHub 链接与法律文档链接
- 主进程与 `window.open` 均改为固定白名单校验

结论：

- “有外链”本身不是发布禁忌
- “可跳任意站点”才是更大的审核和安全风险
- 如果外链保留在 GitHub、内容明确、且与 WoW 相关，风险可控

## MIT 与 EULA 的关系

当前路线是：

- 源代码继续保持 `MIT`
- 应用商店免费分发
- 补充一份面向终端用户的 `EULA`

这条路线可以成立，但要注意：

- `EULA` 不能声称收回 `MIT` 已授予的源代码权利
- `EULA` 更适合承担免责声明、独立第三方声明、支持边界说明、外链说明和本地数据说明

## 当前更适合公开发布的说法

建议保留：

- `独立第三方本地工具`
- `本地账号库、备份、恢复、诊断`
- `不隶属于 Blizzard 或 Battle.net`

建议避免：

- `官方兼容`
- `安全无风险`
- `保证不会封号`
- `完整复刻官方账号管理`

## 建议的发布前剩余动作

1. 持续避免把旧壳文件、旧下载器和远程资源代码重新带回仓库。
2. 检查是否存在任何第三方 Logo、截图、图标或文案被直接复用。
3. 在商店描述和应用内持续保留“独立第三方工具”声明。
4. 在 Partner Center 提交时挂上可公开访问的隐私政策 URL。
5. 避免在商店首屏宣传里过度强调对第三方客户端的底层改写能力。
